# Nexo — prototipo de servicios del campus (Unimet)

Prototipo clicable y responsive (móvil, iPad, escritorio) de **Nexo**, la app de servicios estudiantiles de la Universidad Metropolitana. Nació de wireframes en Figma (archivo `aEHiWasJHowmsGQU07wYGh`, sección `7:79450`) y se desarrolla pantalla por pantalla. Todo está en español (Venezuela).

Es un prototipo: no hay backend. Los datos viven en el navegador (localStorage/sessionStorage) y los pagos, correos y códigos son simulados.

## Cómo correrlo

- Abrir `index.html` directamente en el navegador, o
- `npm run dev` → sirve la carpeta en http://localhost:3000
- Un solo archivo para compartir: `npm run build` → `dist/nexo-prototipo.html` (CSS, JS e íconos adentro; `dist/` no se versiona). Ese archivo no es instalable.
- App instalable (PWA): `npm run build:app` → `dist/nexo-app/` + `dist/nexo-app.zip`, para publicar en un hosting con https (Netlify Drop, GitHub Pages). El script pone la fecha en `VERSION` de `sw.js` para que cada publicación actualice la app instalada.
- **Publicar en GitHub Pages** (activo desde el 15/11/2026, mientras Netlify no tenga créditos): `python3 scripts/deploy_pages.py` arma la PWA y la sube (forzada) a la rama `gh-pages` de `pedroyasellipalomino-spec/NEXO` → https://pedroyasellipalomino-spec.github.io/NEXO/ (Pages: Settings → Pages → Deploy from a branch → `gh-pages` / root). La rama solo guarda la app construida; el código va en `main`. Supabase tiene esa dirección en `uri_allow_list` (los enlaces de correo usan `location`, así que llevan a donde se registró la persona).
- Netlify bloquea publicaciones nuevas cuando la cuenta se queda sin créditos (403 "Account credit usage exceeded"); el script lo muestra. Hasta que el usuario agregue créditos o se renueve el período, no se puede publicar ahí.
- Publicar en Netlify (sitio `nexouni` → https://nexouni.netlify.app, id `fc24f73e-44ed-43df-8f6e-916a33f1422f`): `npm run deploy` (producción) o `npm run deploy:borrador` (vista previa con dirección propia, no toca el sitio real). `scripts/deploy_netlify.py` arma la PWA y sube el .zip a la API de Netlify. En la sesión de Claude Code el token lo pone el proxy (secreto guardado para `api.netlify.com`); fuera, usar `NETLIFY_AUTH_TOKEN`. El dominio `nexouni.netlify.app` no está permitido en la red de la sesión: revisar lo publicado por la API (`/sites/<id>/files`).
- Prueba de humo: `npm test` (necesita `pip install playwright` y `playwright install chromium`)

## Estructura

| Archivo | Qué tiene |
|---|---|
| `index.html` | Todas las pantallas como `<section class="screen" id="…">`. Las que llevan menú lateral/barra son `section.screen.app` |
| `css/styles.css` | Tokens de color en `:root` (+ modo oscuro), componentes y breakpoints |
| `js/data.js` | `MATDB` (código → nombre de materia, 664) y `CARRERAS` (carrera → códigos separados por espacio, 22 carreras), sacados de los flujogramas de pregrado de la Unimet |
| `js/app.js` | Toda la lógica: navegación, cuentas, wallet, pagos, notificaciones, etc. |
| `tests/smoke.py` | Prueba de humo con Playwright |

Orden de carga (importa): Lucide (`vendor/lucide.min.js`, v0.460.0) → Supabase (`vendor/supabase.js`, v2.45.4) → `data.js` → `app.js` (todo local para que funcione sin conexión). Son scripts clásicos, no módulos: comparten el ámbito global, así que `app.js` usa `MATDB`/`CARRERAS` directamente.

## Arquitectura de `app.js`

**Navegación por hash.** `show(id)` muestra una pantalla y oculta las demás; `go(id)` navega. Atributos delegados en el HTML:
`data-go="pantalla"`, `data-go-prev`, `data-toast="mensaje"`, `data-copy`, `data-eye` (ver contraseña), `data-logout`.
Pantallas: tutorial, login, registro, ayuda, inicio, servicios, comida, local, detalle, carrito, comprobante, factura, actividad, estacionamiento, vehiculo, pagoplan, planes, recarga, afiliar, pagomovil, acceso, inscripcion, materias, caja, tarjeta, reserva, revision, qr, soporte, notificaciones, perfil.

**Marco de la app.** Para cada `section.app`, JS construye el menú lateral, la barra móvil (atrás, campana, avatar → perfil), la barra de escritorio (Volver, migas, trimestre, campana) y la barra de pestañas móvil a partir de `data-title`, `data-back`, `data-tab` y `data-crumb`.

**Cuentas y sesión.**
- `localStorage["nexo-accounts"]`: lista de cuentas. La contraseña se guarda transformada con `passKey()`, nunca en claro.
- Sesión en `nexo-session` (localStorage si marcó "Recordarme", si no sessionStorage).
- `isDemo` es verdadero solo para Ana. Al arrancar se eliminan los elementos `[data-new]` (si es demo) o `[data-demo]` (si es cuenta nueva).
- Datos por cuenta con `K("nexo-…")` = clave + `":" + correo`: nexo-pagos, nexo-cards, nexo-nread, nexo-nprefs, nexo-sim, nexo-wallet, nexo-moves, nexo-pendrec, nexo-vehicle, nexo-plan, nexo-materias, nexo-cart, nexo-orders. Si el usuario cambia su correo, estas claves se migran.
- `saveAccount({...})` actualiza la cuenta activa (nombre, correo, carrera, cédula, teléfono, etc.).

**Estado de cuenta / matrícula.**
- Trimestre `TRIM_ID = "2026-sep-nov"` con 3 facturas: septiembre, octubre, noviembre (`MONTHS`).
- Precio por materia: `PRICE_REG = 160`, pronto pago `PRICE_PP = 150` (del segundo lunes del mes hasta ese viernes). Vencen el día 20.
- Estados de factura: pagada, revision, externa, futura, pronto, pendiente, vencida. No se permiten pagos adelantados.
- Las 3 facturas aplican a toda cuenta, aunque se cree a mitad del trimestre. En `#inscripcion` (`#insPaid`, `renderInsPaid`) el estudiante marca los meses ya emitidos que pagó fuera de Nexo → `pagos[id] = { estado: "externa" }` ("Pagada fuera de Nexo", no suma al total pagado en Nexo). Por defecto vienen marcados los meses anteriores a la creación de la cuenta; se puede cambiar al editar las materias.
- Pago por transferencia en `#caja` (módulo "Pago universitario por transferencia"): botón `[data-ut-open]` abre `#utForm`; moneda USD (monto exacto) o Bs. a tasa BCV (−1 %/+5 %) con su cuenta de la universidad; `utCheck`/`utShow` validan fecha (no futura, ≤7 días), banco, referencia no usada en otra factura, monto según las facturas elegidas (`paySel`) y comprobante PDF/JPG/PNG ≤5 MB. Al enviar, cada factura queda `revision` con `ref`, `bank`, `currency`, `paidAmount`, `bcvRate`, `receipt` y `date`; la cuota muestra "Transferencia en revisión · Bs. … ($…) · Ref. …".
- Antes de ver el estado de cuenta, el estudiante registra sus materias en `#inscripcion` (carrera + cantidad + nombre o código). `findSubject(texto, carrera)` resuelve nombre o código contra `MATDB` (sin importar acentos ni mayúsculas).
- `simDate`: chips para simular fechas entre el 1 sep y el 30 nov.

**Estacionamiento.** Wallet Nexo con recargas (tarjeta afiliada o Pago Móvil; el formulario de Pago Móvil valida todo a la vez con `pmCheck`/`pmShow`: prefijo de celular, cédula V/E de 6–8/9 dígitos o RIF J de 9, referencia de 6+ dígitos y no repetida, fecha no futura y de los últimos 7 días, monto en Bs. = recarga × tasa BCV con tolerancia −1 %/+5 %), registro de vehículo (marca, modelo, año, placa), planes (incluye bimestral y trimestral) pagados con saldo y verificación por código de 6 dígitos enviado al correo (simulado: 10 min de validez, reenvío a los 30 s, 3 intentos).

**Comida y kioscos.** Los menús salen de `LOCALES` en `app.js` (10 locales + 3 kioscos: Pincho Pan, La Pausa, Mi Punto Grill, TEEB (empanadas, frituras y comida rápida), Molokai (poke y bowls hawaianos), Sanahoria (comida saludable), Granier (panadería), Pepperonis (pizza), Juice Bar (jugos) y Dey Donuts; los menús de los nuevos son provisionales hasta que el usuario dé las descripciones; cada uno con categorías → productos; `foodOpt()` define grupos de opciones de "elige una" con recargo). Las pantallas `#comida`, `#local`, `#detalle`, `#carrito` se pintan con `renderFoodList/renderLocal/renderDetalle/renderCarrito` desde `show()`; el local y el producto abiertos viven en `sessionStorage["nexo-food"]`.
- Filtros de `#comida` (botón `#ffToggle` en el buscador → panel `#foodFilters`; estado `ff` en `sessionStorage["nexo-ff"]`): solo abiertos ahora (`openState()`: horario de hoy con la hora real + pausa del local; la tarjeta y el menú muestran Abierto / Abre a las… / Cerrado por hoy, pero el prototipo deja pedir igual), precio máximo, tiempo de retiro (máximo del `eta`), tipo de comida (`itemTypes()`: café, almuerzos, bebidas, meriendas, saludable) y orden. `foodMatches()` combina filtros + búsqueda; los activos se ven como etiquetas quitables en `#ffActive`.
- Horario semanal (`weekOf(l)`: 7 días por `getDay()`, `{open, from, to}`; `defaultWeek`: lun–vie el `hours` de `LOCALES`, sábado en la mañana solo La Pausa y kioscos (`SAT_HOURS`), domingo cerrado). El comercio lo edita en `#local-menu` (`#lhForm`, guarda en `localState[id].week`). `openState()` usa el día real y dice "Abre a las…", "Abre mañana…" o "Abre el lunes…" (`nextOpen`); `todayHours(l)` reemplaza a `l.hours` en los textos y `weekTable(l)` muestra la semana en el menú del local. Ojo: `openState` corre al arrancar, no puede usar `hhmm()` (TDZ).
- Retiro programado: en el carrito, "Lo antes posible" solo si el local está abierto (`openState`); si no, o si el estudiante quiere, "Programar el retiro" con día (los próximos 7 días en que el local abre, `dayLabel`) y hora en franjas de 15 min dentro del horario de ese día (`pickupSlots`, `cartPickup`, guardado en `cart.pickup`). Al confirmar, el pedido guarda `scheduledFor`, `readyAt` y `prepStart` (= retiro − `etaMax`); `orderStatus()` da "programado" hasta `prepStart`, luego "preparando" (aviso `prepNotified`) y "listo". El comercio lo ve en su columna de preparación con la hora programada. La prueba de humo fija la fecha y hora (miércoles 11 nov 2026, 12:30) para no depender del reloj real.
- Carrito por cuenta en `nexo-cart` (`{ local, lines:[{item, sel, qty, note}] }`): un solo local por pedido; al añadir de otro local se avisa y se vacía. La cuenta demo arranca con el almuerzo del día de Pincho Pan.
- Pago con tarjeta (simulado) → crea el pedido y va a `#pedido` (seguimiento). Transferencia → `#comprobante` (borrador `draftOrder`; moneda USD o Bs. con su cuenta destino; `cpCheck`/`cpShow` validan fecha no futura y de ≤7 días, banco, referencia de 6+ dígitos no usada en otro pedido, monto exacto en USD o en Bs. a tasa BCV con −1 %/+5 %, y archivo PDF/JPG/PNG de ≤5 MB) → al enviar, se confirma; el pedido guarda `ref`, `bank`, `currency`, `paidAmount`, `receipt` y `bcvRate`. Los pedidos se guardan en `nexo-orders` y se agregan a Actividad con `addMovement(..., { order })`; el botón lleva `data-order` para abrir esa factura.
- `#factura` sin pedido elegido: la cuenta demo ve la factura de ejemplo (`FC_SAMPLE`); las demás ven su último pedido o un estado vacío (nunca datos de Ana).
- Seguimiento (`#pedido`, `renderPedido`): al confirmar, el pedido guarda `paidAt`, `readyAt` (= pago + punto medio del `eta` del local, `prepMinutes`) y `code` (`pickupCode`, 4 dígitos). `orderStatus()`: preparando → listo (al pasar `readyAt`) → retirado (`pickedAt`, botón "Ya lo retiré"). `checkOrders()` corre cada 15 s: avisa con toast y `foodNotifs()` agrega la notificación (va a `#pedido` con `trackId`). En `#comida`, `#foodOrders` muestra los pedidos activos. Hay un enlace de prototipo para simular que ya está listo. `drawQR(canvas)` dibuja el QR ilustrativo.

**Roles y soporte (Figma sección `7:79457` · 08 Roles y gestión).** Las cuentas tienen `role`: estudiante (por defecto), `creator`, `admin`, `mod` o `local` (`roleOf()`); `disabled` (desactivar desde el equipo) **no** bloquea el login: la cuenta conserva su `role` guardado, pero `roleOf()` devuelve "estudiante", así que entra como usuario sin acceso de gestión hasta que la reactiven. Las cuentas de gestión de ejemplo están en `STAFF0`.
- Las pantallas de gestión llevan `data-staff="admin"|"mod"`: el marco usa `STAFF_NAV` (menú propio, botón Salir, sin campana). `show()` redirige según `STAFF_SCREENS`/`ROLE_HOME`: el estudiante no entra a gestión; cada rol solo entra a su gestión; los comercios no entran a pantallas de estudiante.
- **Modo usuario:** creador, admin y moderador también pueden usar las pantallas de estudiante con su cuenta (pedir comida, estacionamiento, canchas, soporte). El último modo se guarda en `nexo-mode:<correo>` y al iniciar sesión vuelven a él (`#inicio` o su inicio de gestión). Las cuentas sin carnet no ven el estado de cuenta universitario (materias/caja/tarjeta/inscripcion redirigen al inicio y se ocultan sus accesos; `#revision` es el pago de canchas y no pide carnet).
- **Menú de usuario** (`openUserMenu`, módulo "Menú de usuario y cambio de modo"): lo abre cualquier `[data-usermenu]` (avatar de la barra móvil y de escritorio, y el perfil del menú lateral). Muestra datos de la cuenta, el selector Modo gestión / Modo usuario (solo personal), Mi cuenta, Notificaciones, Actividad, Soporte y Cerrar sesión; en móvil es una hoja inferior. Se cierra con Esc o al tocar fuera. En modo usuario hay además un botón "Ir a gestión" en la barra y "Volver a gestión" en el menú lateral (`[data-mode-switch]`).
- Administración: `#gestion` (indicadores, tabla filtrable, asignar moderador, exportar CSV, invitar), `#equipo` (activar/desactivar, cancelar invitaciones), `#caso` (ticket en solo lectura). Moderación: `#moderacion` es una bandeja con pestañas Mis tickets / Sin asignar / Todos abiertos (`mdTab`), buscador y filtro por servicio; cualquier moderador responde cualquier ticket abierto (si no tiene responsable, `mdTake` se lo asigna al responder; si es de otro, avisa y permite "Tomar este ticket"), respuestas rápidas (`MD_TEMPLATES`), notas internas (`messages` con `from: "note"`, `convHTML` las oculta al estudiante), cambiar prioridad, liberar, "Esperar respuesta del estudiante" (estado `espera`, vuelve a `revision` cuando el estudiante responde), reembolsar/cancelar con confirmación y resolver/reabrir; `#resueltos` lista los propios resueltos.
- Los tickets son **globales** en `localStorage["nexo-tickets"]` (no por cuenta), sembrados con `seedTickets()`. Las invitaciones en `nexo-invites` (`newInvite`: `role`, `token`, `exp` a 7 días, `byName`). La persona invitada activa su cuenta **sin carnet** en `#invitacion` (pantalla pública): por enlace `#invitacion-<token>` ("Copiar enlace" en el equipo) o buscando su correo; si intenta registrarse como estudiante con ese correo, se la desvía ahí. Vencidas se reenvían (token nuevo) desde el menú ⋯ del creador. Un reembolso agrega un movimiento a `nexo-moves:<correo del estudiante>`.
- Creador (Figma `2:25763` y `2:25970`): `#creador` (indicadores, gráfico de ingresos por comisiones con tooltip y vista de tabla, compras por servicio; métricas de ejemplo en `PERIODS`, ingresos = volumen × comisión), `#creador-equipo` (equipo con menú ⋯ para cambiar rol/desactivar, invitar admin o moderador, centro de soporte con respuesta, reembolso, cancelación y resolver), `#movimientos` (transacciones de `nexo-orders:*` y reembolsos + registro de cambios) y `#config` (comisiones por servicio en `nexo-config`, restablecer datos de ejemplo). Movimientos y Configuración no tienen diseño en Figma.
- Caja · `#validar` (admin y creador; `STAFF_SCREENS.validar` es una lista de roles y `relabelForCreator()` le pone el menú del creador; sin diseño en Figma): junta de todas las cuentas las facturas en revisión (`nexo-pagos:<correo>`) y las recargas por Pago Móvil (`nexo-pendrec:<correo>`) con monto USD/Bs., banco, referencia y comprobante (`cajaItems`). Aprobar → factura `pagada` (via "Transferencia"/"Transferencia en Bs.") o recarga `aprobada` + saldo sumado a `nexo-wallet:<correo>`; rechazar con motivo → factura `rechazada` (vuelve a quedar por pagar, con el motivo en la cuota) o recarga `rechazada`. Actualiza el movimiento del estudiante (`vlUpdateMove`), genera su notificación y queda en auditoría (tipo `caja`). Pagos de ejemplo sembrados una vez (`nexo-cajaseed`).
- Registro de auditoría global en `nexo-audit` con `logAudit(tipo, texto)`; las acciones de tickets compartidas son `ticketReply`, `ticketAction` y `ticketResolve`.
- Comercio (`role: "local"`, la cuenta lleva `local: <id>`; sin diseño en Figma): `#local-pedidos` (tablero En preparación / Listos / Entregados hoy; marcar listo, demora +5 min, cancelar con reembolso al estudiante, entregar verificando el código de 4 dígitos, pausar pedidos) y `#local-menu` (productos agotados, pausa). El comercio lee y escribe los pedidos en `nexo-orders:<correo del estudiante>` (`allOrders`, `updateOrder`); siembra pedidos de ejemplo una vez por local (`nexo-localseed:<id>`). Agotados y pausa viven en `nexo-localstate` (global) y la vista del estudiante los respeta (no deja abrir, añadir ni pagar). Si el local no actúa, el pedido igual pasa a listo por tiempo. Un listener de `storage` refresca las pantallas cuando otra pestaña cambia pedidos, tickets o el estado de un local (dos pestañas con cuentas distintas: iniciar sesión sin "Recordar").
- Estudiante: `#soporte` lista sus tickets (`renderSoporte`), crea solicitudes (`#supForm`, puede ligar un pedido de `nexo-orders`) y responde en la conversación.

**Avisos, deshacer y confirmar.** `toast(msg, { action, onAction, persist })`: los avisos con acción duran 6 s; los persistentes (pedido listo) se apilan y se cierran con ×. Hay "Deshacer" al quitar un producto del carrito (`undoCartToast(snap)`), al vaciarlo por añadir de otro local y en "Marcar todas como leídas". `askConfirm({ icon, title, text, ok, cancel, danger, onOk })` es el diálogo de confirmación genérico; se usa antes de cerrar sesión con pedidos en curso (`doLogout`).

**Inicio inteligente.** `#homeNow` ("Para ti ahora", arriba de `#inicio`): `homeItems()` junta pedidos en curso o listos, facturas (rechazada, vencida, pronto pago, por vencer), plan de estacionamiento por vencer o vencido, recargas rechazadas sin leer y tickets abiertos cuya última respuesta es del moderador; prioridad `pr` (0 = más urgente), muestra 3 y "Ver todo". Se pinta en `show("inicio")` y cada 15 s.

**Pedir de nuevo y favoritos.** Las líneas de cada pedido guardan `item` y `sel` (los pedidos viejos se reconstruyen por nombre y por el texto de las opciones). `reorder(o)` arma el carrito (salta agotados, respeta la pausa, "Deshacer" si había otro carrito); botón `[data-reorder]` en `#pedido` (listo, retirado o cancelado) y en `#foodAgain` de `#comida` (`renderFoodAgain`: últimos 3 pedidos distintos + favoritos). Favoritos por cuenta en `nexo-favs` (`"local:item"`); el corazón `favBtn()` es un botón hermano de la tarjeta del producto (`.favwrap`), nunca anidado.

**Pulido.** `emptyState(icon, título, texto, acción)` da el mismo estado vacío en todas las listas (clase `.empty`). Formularios: Enter pasa al siguiente campo y pone `enterkeyhint` (último = enviar); con 4+ campos el botón de enviar queda fijo abajo en móvil (`.longform`). Botón atrás (`[data-back-btn]` en la barra móvil y "Volver"): usa el recorrido real `navTrail` (sessionStorage `nexo-trail`, se reinicia al iniciar sesión), salta pantallas de paso (`NO_BACK`, carrito vacío, cambio gestión/usuario) y si no hay a dónde volver usa `data-back`. Modo demostración (`nexo-demomode:<correo>`, interruptor en Mi cuenta; activo por defecto solo en la cuenta demo): sin él, `body.no-demo` oculta `.demo-only` (fecha simulada, simular pedido listo) y la fecha vuelve a hoy. Textos: "Pago Móvil" con mayúscula y enlaces con "→".

**Accesibilidad.** Textos secundarios a 12 px mínimo (`.tiny`, `.move span`, `.bsv`, etc.) y `--muted` más oscuro en claro (#55696e, 5,8:1 sobre blanco). Al navegar (`hashchange`), `focusScreen()` lleva el foco al `h1` de la pantalla (con `tabindex="-1"`, salvo que la pantalla ya haya enfocado un campo) y lo anuncia en `#srLive` (`.sr-only`). Apariencia global en `nexo-theme` (`light`/`dark`; sin clave = automático): un script en `<head>` la aplica antes de pintar; selector `.seg` (`themeSeg()`, `[data-theme-set]`) en Mi cuenta y en el menú de usuario. Los colores fijos nuevos llevan su versión oscura con los dos selectores (`@media (prefers-color-scheme:dark){:root:not([data-theme="light"]) …}` y `:root[data-theme="dark"] …`).

**Para el personal.** Avisos en vivo (`liveKeys()`/`liveCheck()`): con cada evento `storage` de otra pestaña se comparan las claves de lo que le importa al rol (tickets abiertos sin asignar y respuestas de estudiantes en los propios para moderación; tickets abiertos para admin/creador; pagos por validar en Caja; pedidos activos del comercio) y lo nuevo sale como toast persistente con "Ver", un sonido corto (WebAudio) y el contador en el título si la pestaña está oculta; lo que cambia en la misma pestaña no se avisa. Acciones en lote: casillas en Caja (`vlSel`, barra `#vlBulk`, "Aprobar N" con `askConfirm`, `vlDecide(…, quiet)`) y en Gestión (`gsSel`, barra `#gsBulk` con moderador, `assignTicket(…, quiet)`). Satisfacción: al resolverse un ticket con responsable, el estudiante lo califica 1–5 en `#soporte` (`rateHTML`, `t.rating`); el equipo muestra el promedio por moderador (`rateSummary`). Calificaciones de ejemplo sembradas una vez (`nexo-rateseed`).

## Cómo trabajar con el usuario

- Publicación automática: cada cambio terminado y con la prueba de humo en verde se publica de una vez en GitHub Pages (`python3 scripts/deploy_pages.py`) y se le da al usuario el enlace https://pedroyasellipalomino-spec.github.io/NEXO/. Netlify (https://nexouni.netlify.app) queda con la versión del 13/11 hasta que tenga créditos. Si la prueba falla, no se publica.
- Respaldo: el código vive en GitHub, `pedroyasellipalomino-spec/NEXO` (rama `main`, la cuenta del usuario; nunca usar otra). Después de cada commit, `git push origin main`.
- Registro de cambios: cada cambio se anota arriba en `CAMBIOS.md` (fecha, menos de 10 palabras) y se le envía el archivo al usuario después de cada cambio.
- Cuando haya que elegir entre opciones (qué mejorar, decisiones de diseño, etc.), preséntalas siempre como un formulario de un clic (herramienta de preguntas con opciones), no como una lista en texto. Marca la recomendada.

**Tasa BCV y bolívares.** `BCV` (módulo junto a `money()`) guarda la tasa oficial del dólar: valor inicial `BCV0` = Bs. 915,74 del 16/11/2026, indicado por el dueño (fuente oficial: bcv.org.ve; antes 911,22 del 14/11 y 901,62 del 11/11). Una tasa guardada en `nexo-bcv` con fecha anterior a la de `BCV0` se ignora. El creador la actualiza en `#config` (formulario `#bcvForm`, `nexo-bcv` global, queda en el registro de cambios). Helpers: `bcvRate()`, `bsOf(usd)`, `bsAmt(bs)`, `bsTag(usd)` (`<span class="bsv">`), `bcvDateTxt()`, `bcvStale()`. Se muestran equivalentes en Bs. en Inicio (pill), menús, detalle, carrito, pedido, planes, recarga, facturas por pagar y Pago Móvil; `refreshBcvUI()` refresca lo estático.

## Convenciones

- Textos de interfaz en español, tono cercano (tú). Montos con `money(n)` → `$1.234,56`.
- Íconos: Lucide (`<i data-lucide="nombre">`); llamar `lucide.createIcons()` tras insertar HTML nuevo.
- Usar `el.hidden` para mostrar/ocultar (hay `[hidden]{display:none!important}`).
- Envolver todo acceso a localStorage en `try/catch`. Al inicio de `app.js` hay un respaldo: si el navegador bloquea localStorage/sessionStorage (vistas previas, iframes aislados), se usa `window.name`, que sobrevive a las recargas de la pestaña. No quitarlo: el registro y el login recargan la página.
- Código nuevo de pantallas: insertarlo en `app.js` antes del bloque `document.querySelectorAll("form[data-submit]")`.
- Al tocar algo que se inicializa al arrancar, cuidado con el orden de `let`/`const` (ya hubo errores de TDZ con `plan` y `vehicle`).
- Nunca `<input type="date">` ni `type="time"`: en es-VE Chromium pone el mes primero y la hora en a. m./p. m., y confunde (no dejaba cambiar el día). En su lugar: fecha de nacimiento con tres listas Día/Mes/Año (`dobFill`, `dobDays`, `dobSync` → `#pf-birth` oculto, AAAA-MM-DD); fechas de pago (`#pm-date`, `#cp-f`, `#ut-f`) con `select[data-recent-days="7"]` ("Hoy, 12 nov", "Ayer, 11 nov"…; `recentDayOpts`/`fillRecentDays`, se refrescan en cada `show()`); fecha valor de la tasa BCV con los últimos 14 días; fecha de simulación con los días de sep–nov agrupados por mes; horario del comercio con `timeOpts()` (24 h, cada 15 min). Todos guardan el mismo formato que antes (AAAA-MM-DD y HH:MM).
- No pedir ni mostrar datos reales de tarjetas; los datos de Pago Móvil de destino son ilustrativos.
